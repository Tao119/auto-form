## 問題 1：住所欠落（89.2%）

### 原因

n8n ワークフローの `最終データ整形`（Set ノード）が `address` フィールドをアサインせず、
`完了コールバック`（HTTP Request ノード）の body にも `address` キーが含まれていなかった。

Google Places API は `formattedAddress` を返しており、`企業データを整形` ノードで
`address` として取り出しているが、その後のフローで落としていた。

### 影響範囲

| 業種 | 住所あり | 住所なし | 備考 |
|------|---------|---------|------|
| 歯科 | 0 | 704 | 全件なし |
| 整骨院 | 0 | 291 | 全件なし |
| 美容室 | 10 | 268 | 旧インポート分10件のみあり |
| その他 | 143 | 0 | 旧Sheetsインポート分（住所あり） |

### 修正状況

- `/tmp/workflow_address.json` に修正済み（`最終データ整形` + `完了コールバック` 両方を更新）
- Docker 復帰後に `PUT /api/v1/workflows/thgFkhf2la4ZOGU0` で適用予定

## 問題 2：LINE URL の誤分類（14.7%）

### 概要

Playwright が LP内のLINE公式アカウントリンク（`lin.ee/...`, `page.line.me/...` 等）を
「問い合わせ手段」として取得し、GPT スタブが無条件に `formType: inquiry` に分類していた。
実際には LINE Messenger へのリダイレクトであり、Web フォームではない。

整骨院・美容室はLINE予約を主力とする店舗が多く、LINE率が高い傾向。

### 修正状況

**修正完了（2026-04-16）**

1. `companies-db.ts` に `isLineUrl()` 関数を追加
2. `addCompanies()` で LINE URL を検出し `formType: 'LINE'` に上書き
3. DB起動時マイグレーションで既存208件を一括更新済み
4. リスト画面にフォーム種別フィルター（inquiry / LINE / unknown）を追加
5. LINE URL を orange 色で視覚的に区別表示

## 問題 3：収集日時の欠落

`collectedAt` が全1,416件で空文字になっている。

### 原因

n8n ワークフローの `完了コールバック` body に `collectedAt` フィールドが存在するが、
`最終データ整形` ノードが `new Date().toLocaleString()` 形式で設定しており、
`addCompanies()` のフォールバックで `collectedAt || new Date().toISOString()` が使われているはず。

ただし、実際にDBに入っているのは全件空 → コールバック body の `collectedAt` が受け渡されていない可能性。

### 影響

フィルタリングや時系列分析に支障あり（現時点では軽微）。

## 問題 4：formType の精度（GPT スタブ）

現在の L-04 は GPT を使用せず、全件 `message.type = 'inquiry'` を返すスタブ。
実際には以下の種別が存在するが、未分類のまま：

| 推定種別 | 説明 | 件数推定 |
|---------|------|---------|
| inquiry | 問い合わせフォーム（本来の対象） | ~1,151 |
| reservation | 予約フォーム（ホットペッパー等） | 未計測 |
| LINE | LINE公式アカウント | 208（修正済み） |
| recruitment | 採用フォーム | 未計測 |
| unknown | 判別不能 | 57 |

GPT分類を有効化すれば精度向上するが、コスト増（gpt-4o-mini: ~$0.0001/件 → 1,000件で$0.1程度）。
